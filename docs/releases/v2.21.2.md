# GRACEFELL v2.21.2 release record

Date: 2026-07-25
Owner: @jonathanwxh-cell
Implementation and verification: Codex with three independent game-menu review agents

Status: implementation candidate; merged-SHA deployment evidence must be appended after release

## Outcome

The title screen now presents one coherent game-menu hierarchy on desktop and
mobile. The primary action, selected trial, trial effects, safety settings,
saved results, Records utility, and keyboard companion no longer compete as
separate visual systems.

This is a presentation and semantic-input release. It does not change combat,
difficulty values, boss patterns, weather, music, sound effects, scoring,
persistence, touch hit targets, runtime assets, or per-frame particle work.

## Why this round existed

v2.21.1 repaired a real short-phone overlap by anchoring compact title copy to
the measured menu plate. A fresh 1280x800 desktop audit with saved progress then
showed that the desktop branch still used independent viewport percentages:
saved results and the start prompt were only six pixels apart. At 1920x1080,
the fixed-width settings plate also looked like a phone utility beneath an
oversized logo.

After the measured collision was repaired, the menu was technically correct but
still felt inconsistent. The owner therefore requested several autonomous
reviewers and multiple rounds rather than a single subjective redesign.

## The autonomous review workflow

Three bounded roles reviewed the same live local candidate independently:

1. **Art direction and hierarchy**
   - judged typography, scale, material language, visual rhythm, and whether the
     screen felt like a game menu rather than a settings dashboard;
   - proposed the compact “Trial Seal” direction.
2. **Player-facing information architecture**
   - reviewed the first-time and returning-player reading order;
   - identified the anonymous `PATH / JOURNEY -2` row, mixed copy voices, and
     equal visual weight between difficulty and safety options.
3. **Interaction and accessibility**
   - exercised keyboard focus, pointer dismissal, native controls, focus order,
     backdrop ownership, and narrow mobile layout;
   - separated semantic control correctness from Canvas presentation.

### Round one: findings before implementation

All three reviewers agreed on the root problem: the title read as a logo plus a
settings dashboard. The first settings row did not explicitly say
`DIFFICULTY`, the thematic trial name and numeric path notation competed, and
the start prompt did not clearly dominate the secondary settings.

The convergence rule was deliberately conservative: implement only findings
shared across roles or supported by measured layout/input evidence. No Figma
file, generated texture, new runtime asset, shader, second particle system, or
continuous animation was introduced.

### Synthesis: one Trial Seal

The accepted direction preserved the existing circular arena and gold/ink
language while establishing one reading order:

1. `GRACEFELL` and the existing subtitle;
2. saved record, when present;
3. `RAISE YOUR BLADE` as the only primary action;
4. one named Trial Seal with plain-language effects;
5. subordinate safety settings;
6. compact platform-specific input guidance.

The menu geometry remained authored by `menuGeom()`. Wide desktop scale is
capped at 1.2x, so legibility improves without producing a full-width settings
dashboard. Compact screens retain the complete five-row touch menu.

### Round two: adversarial retest

The same three roles retested the implementation at 1280x800, 1920x1080, and
390x844. No reviewer recommended a structural rewrite. The remaining actionable
finding was interaction-specific:

- Enter on native `Combat tips` was consumed by the Canvas game input handler;
- the optional disclosure preceded the primary action in keyboard focus order.

The final correction treats `summary` and `details` as native interactive
targets, moves Combat tips after the primary action group, and proves that Enter
opens the disclosure without advancing `confirmSequence`. Keyboard focus also
reveals a real dismissible veil; Escape or backdrop activation restores focus
to the Canvas title.

## Presentation details

- The wordmark is drawn once with measured Canvas letter spacing instead of
  literal spaces between characters.
- Desktop labels the selector `CHOOSE DIFFICULTY`; compact layouts use
  `DIFFICULTY`.
- The selected trial is named semantically, for example
  `JOURNEY · GUIDED`, while the compact Canvas value stays `JOURNEY`.
- Journey effects use plain copy such as `Slower foe`,
  `Less damage taken`, and `4 flasks`.
- Desktop input guidance is key-first:
  `WASD MOVE · SPACE ROLL · J ATTACK · K HEAVY · F FLASK`.
- Touch guidance names the left and right thumb roles.
- Safety settings use open hairlines and lower emphasis rather than another
  filled plaque.
- The title utility is named `RECORDS`; its persistence and dialog behavior are
  unchanged from the earlier Scores chronicle.

## Performance and safety boundary

The change adds no runtime image, font, audio, fetch, timer, persistent render
pass, particle pool, blur surface, or gameplay state. Canvas work remains
bounded to title rendering; the semantic veil exists only while keyboard
controls own focus. Combat, weather, audio graph, save schema v7, and touch
geometry remain unchanged.

## Acceptance contract

Before merge:

- `npm run lint`;
- `npm test` (19 tests);
- `npm run build`;
- `npm run qa`;
- screenshot review for desktop, mobile, and keyboard-focus states;
- `git diff --check`;
- clean-runner GitHub Actions acceptance.

The menu-specific QA requirements are:

- zero desktop, mobile, and true-touch document overflow;
- positive separation between difficulty label, pip scale, and selected trial;
- semantic primary action before optional Combat tips;
- Enter on Combat tips does not change the game confirmation sequence;
- focus veil is present and dismissible;
- no console errors.

## Rollback boundary

The implementation is confined to title rendering, the semantic companion,
theme CSS, QA, version metadata, and documentation. A rollback does not require
a save migration or asset cleanup because no persistence schema or runtime asset
changed.
