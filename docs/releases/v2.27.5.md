## Outcome

An earned stagger is now one authoritative combat opening. If the
poise-breaking hit also crosses Malakar's 55% or 22% phase threshold, the
complete stagger remains available and the existing phase ring begins once
afterward. Execute owns the central prompt, semantic combat status, and touch
heavy label until consumed. Once consumed, the same opening shows ordinary
HVY and cannot promise a second Execute, Sunder, or Gracebreak. Full Resolve
remains visibly stored as `RESOLVE FULL`, while Break action copy and semantic
readiness return only after the stagger ends.

No damage, poise, stamina, Resolve, health, stagger duration, phase action,
difficulty, scoring, save, audio, asset, touch target, camera, or rendering
value changed.

## Root cause

The simulation exposed several local tests of stagger instead of one
capability. Phase thresholds did not respect the newly awarded stagger state,
presentation treated `state === 'staggered'` as Execute-ready even after
consumption, and transient Sunder copy could outrank the action the same hit
had just earned.

## Research boundary

- [Apple game controls](https://developer.apple.com/design/human-interface-guidelines/game-controls)
  supports precise, intuitive controls with feedback that reinforces the
  control state.
- [Xbox Accessibility Guideline 107](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/107)
  treats timing and input complexity as accessibility constraints and expects
  alternate inputs to retain the same functionality.
- [Xbox Accessibility Guideline 103](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/103)
  recommends communicating critical information through more than one sensory
  channel rather than color alone.

Those principles supported one cross-surface authority and exact input-route
verification. They did not justify a new action, control, system, or global
balance change.

## Implementation

- `Boss.executeReady` is the single execution capability.
- Phase 1→2 and 2→3 transitions defer while the boss is staggered.
- Execute-ready feedback outranks transient Sunder in Canvas and semantic UI.
- The touch heavy button exposes `EXECUTE` only while execution is available.
- The Resolve rail and aria-live status distinguish stored `Resolve full` from
  an actionable Break; generic Break/Sunder hints are suppressed during
  stagger and restore afterward.
- Successful execution announces `EXECUTE`; a consumed opening exposes
  ordinary `HVY` and preserves Resolve.

## Adversarial verification

The first QA review found four proof gaps: approximate instead of exact stagger
duration, direct input-buffer injection instead of real events, uncounted phase
side effects, and snapshot-only semantic checks. The amended lane now:

- proves the exact difficulty-derived opening and frame count;
- counts phase set, phase banner, arena deepening, and scar stamping exactly
  once, separately from the stagger banner;
- uses a genuine Playwright touchscreen tap and desktop `K` event;
- reads the actual `#game-combat-status` DOM before and after Execute;
- asserts `Execute ready → EXECUTE` on both input surfaces;
- verifies one 109.2-damage Execute, preserved Resolve `100`, zero Resolve
  uses, and a later ordinary 42-damage heavy.
- verifies the natural Execute `89→100` Resolve gain cannot overwrite
  `EXECUTE`, announce Break, or make semantic Gracebreak ready.

The first visual review then caught `BREAK READY` persisting on the full meter.
After that repair, the runtime reviewer found the separate 89→100 announcement
and aria-live paths. Both were fixed and locked before the candidate froze.
Headless verification cannot prove physical haptics, thumb latency,
phone-speaker mix, or iOS Safari behavior.

  unchanged.

revert, restart `gracefell.service`, and rerun public QA. No data or save
migration is required.
