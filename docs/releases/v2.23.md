# GRACEFELL v2.23 release record — render-cost gate

Date: 2026-07-26
Owner: @jonathanwxh-cell
Implementation and verification: Claude (Opus 5 / Claude Code)

Status: local acceptance complete

## Outcome

This release adds a render-cost gate and **ships no engine change**. Four
Canvas2D optimisations were implemented, measured, and rejected on their own
evidence. The measurement instrument is the deliverable; the negative results
are recorded so the next agent does not pay for them again.

Combat, boss behaviour, difficulty, input, scoring, persistence, save schema v7,
weather, music, and sound effects are untouched. `src/game/engine.ts` is
byte-identical to v2.22.1.

## Why the pass started

A polish request needed performance headroom to spend. The renderer looked like
it had obvious slack: 41 `createRadialGradient` calls per frame, 9 `shadowBlur`
sets, and only 2 `drawImage` calls, meaning almost nothing was cached. The
working estimate was 2–3 ms/frame recoverable on mobile.

That estimate came from tight-loop micro-benchmarks, and it was wrong by an
order of magnitude.

## Why the existing timing check could not settle it

`qa/verify.cjs` asserts that phase-three weather adds under 0.5 ms median by
timing single `render()` calls. Two platform properties defeat that:

- `performance.now()` is clamped to roughly 100 µs, so one render is a handful
  of ticks wide;
- Canvas2D defers rasterisation, so timing a render call measures command
  submission, not pixels.

Measured frame-to-frame baseline drift on the development laptop was ±20% —
an order of magnitude above the threshold being asserted. Three separate
micro-benchmark rounds produced three contradictory answers, including a
`drawImage`/`fill` relationship that inverted between headless (software
raster) and headed (GPU) runs.

## The method that did settle it

All candidate builds served simultaneously on separate ports, all pages open at
once, and measurement blocks **alternated between them** so machine drift moved
every variant together. A second copy of the *same* build was measured
alongside as a control, establishing the noise floor empirically rather than
assuming it.

Mobile 390×844 dpr2, real GPU, 60–70 interleaved blocks of 25 renders each,
worst-case pinned phase-three scene (420 particles, 32 projectiles, 9 meteors,
3 rings, low-HP vignette, both full-screen flashes):

| variant | median | vs base |
| --- | --- | --- |
| baseline | 1.656–1.912 ms | — |
| **control (identical build)** | — | **+0.5%** ← noise floor |
| pre-baked sprites for glow particles | — | **+17.6%** |
| pre-baked sprite for projectile glow | — | −1.5% / −3.5% (two runs) |
| offset double-draw instead of `shadowBlur` | — | −1.4% |
| baked static vignette instead of gradient fill | — | +1.9% |

Only the particle result sits outside the noise, and it is a loss: converting
roughly 500 small flat-colour arc fills into `drawImage` blits made the frame
17.6% slower, with non-overlapping interquartile ranges. Everything else is
indistinguishable from measuring the same build twice.

A seeded-`Math.random` pixel diff of the same pinned scene put the projectile
sprite at 5.5% of pixels changed against a 1.6% same-build control, mean channel
delta under 1/255 — sub-perceptual, but not the "zero visual change" that had
been claimed for it.

## The finding that matters

**This renderer has no meaningful slack to reclaim.** A worst-case phase-three
frame costs about 1.7 ms on a desktop GPU at 390×844 dpr2 — roughly a tenth of
a 16.7 ms budget. Future visual work should not be gated on finding headroom in
the draw path, because the headroom is already there.

The risks actually worth managing are per-frame **allocation** (GC pauses on
phones) and **low-end mobile GPUs**. Neither is visible from a desktop timing
run, and neither is what the rejected changes addressed.

## What shipped

`qa/perf.cjs`, wired into `npm run qa` and available as `npm run perf`
(adds `--timings`). It asserts a **deterministic op census** rather than a
duration, because canvas call counts for a pinned scene do not vary with
machine load at all:

- `createRadialGradient` ≤ 52 per frame (measured 41);
- **gradients per projectile ≤ 1.2** (measured 1.0) — censused against a
  no-projectile scene, so it catches per-entity gradient growth even when the
  absolute count still fits;
- `shadowBlur` set non-zero ≤ 12 per frame (measured 9);
- draw calls ≤ 1100 (measured 908 mobile / 889 desktop);
- the census must be identical across two consecutive frames.

That last assertion already earned itself: it caught a lazily-built sprite cache
allocating on its first frame only, which a single-frame census would have
reported as a clean pass.

## Known limits

- All timings are from one Windows laptop with an Intel Arc GPU via ANGLE/D3D11.
  Absolute numbers do not transfer to a phone; the interleaved comparisons and
  the control are what carry.
- The op census is machine-independent and is the part that gates CI.
- No on-device measurement was taken. The mobile-GPU and GC questions above
  remain open.
